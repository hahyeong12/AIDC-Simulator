> 문서 작성: 2026-11-11. 기준: `main`의 `v0.9-3b`, 커밋 `f044c74`.

## 2. 개발의 새로운 우선순위

### P0 — 현재 게임 보존 및 기준선 확정

- 최신 `main`과 버전·문서·GUI 상태 확인.
- GUI 테스트, 전체 Chapter 정상/실패/재도전/저장·이어하기 스모크 테스트.
- 현재 자유 운영과 Chapter 1~3b의 게임 규칙, 자원 원장, 고객 동의, 점수/기한 보존.
- 문서에서 과거 단계 설명과 현재 구현 상태를 구분.
- **완료 조건:** 문제 재현·수정 내역과 테스트 실행/미실행 내역이 분명하고 기존 시나리오가 회귀하지 않음.

### P1 — 작은 '네트워크 가시화' 수직 절단면

- 기존 Chapter 3a 사건 **한 개**를 골라 고객→라우터/게이트웨이→서버 경로를 교육용 도식으로 표현.
- 패킷/요청/응답의 이동, 장애 구간, 상태 변화를 단계별로 표시.
- 네트워크 경로/링크/IP/서비스 상태가 서로 다른 개념임을 구분.
- 먼저 네트워크 모형과 시각화 사이의 계약을 정의하고, 기존 Chapter 3a 결과를 변경하지 않는 조회형으로 시작.
- **완료 조건:** 장애 전/후 구조·진단 근거·조치 결과가 같은 시뮬레이션 상태로 일관되게 표현됨.

### P2 — 의미가 보이는 명령어 선택·조립

- 자연어 질문("어떤 경로로 가는가?") → 기능 설명이 있는 명령어 객관식 → 명령어와 옵션/대상 조립.
- 3~5개 정도의 명령어를 우선 선정하되 실제 정확한 명령 수는 구현 검토 후 결정.
- 정답만 출력하는 퀴즈가 아니라 명령어 실행 결과를 P1 구조도에 반영.
- **완료 조건:** 플레이어가 명령의 목적과 출력 의미를 이해하고, 잘못된 명령 선택에서 적절한 학습 피드백을 얻음.

### P3 — 게임 상태와 연결된 안전한 가상 Linux 터미널

- 제한된 명령 구문을 해석하는 가상 터미널. 운영체제의 실제 셸과 구별.
- 현재 가상 서버/라우팅/서비스 상태에서 출력 생성; 읽기/조치 명령을 구별.
- 기존 `GameSession`과 별도 관측/명령 인터페이스로 통합; 모든 규칙을 GUI 곳곳에 중복 구현하지 않음.
- **완료 조건:** GUI에서 확인한 원인과 명령 출력이 일치하고, 명령에 따른 변경·시간·로그·결과가 회귀 테스트로 검증됨.

### P4 — 숙련도 상승과 독립 문제 해결

- 기존 Chapter 1~3b는 기초 운영 교육으로 유지하고, 이후에 구조 관찰/명령어 교육을 연결.
- 객관식 → 블록/옵션 구성 → 부분 힌트 → 자유 입력으로 도움의 양을 줄임.
- 같은 '증상'에 서로 다른 근본 원인(DNS/라우팅/서비스 등)을 가진 복수 시나리오를 만들어 성급한 결론을 막음.
- **완료 조건:** 최소 1개 미션에서 '상황 파악→관찰 명령→증거 해석→조치→사후 검증'이 힌트 없이 끝까지 진행됨.

### P5 — 통합 시연 및 v1.0 범위 합의

- 완성된 교육 루프 하나를 전체 사용자 경험으로 다듬고 UI·튜토리얼·성공/실패·저장을 검증.
- README에 실제 플레이 방법, 스크린샷, 시연 자료, 지원 명령어와 교육용 단순화, 제한사항을 정확히 기재.
- 온라인 전시용 짧은 시연을 구성.
- **완료 조건:** 처음 보는 사람이 시연을 따라하고 '왜 이 프로젝트는 단순 운영 버튼 게임과 다른가'를 설명할 수 있음.

## 3. 학기 프로젝트와 장기 비전 분리

**학기 마감까지 우선할 목표(권장):** 기존 게임 안정화 + 한 가지 네트워크 구조의 시각화 + 선택/조립을 거쳐 가상 명령으로 진단하는 **작지만 완결된 학습 루프** + 제출 시연·문서.

**장기 목표:** 다양한 명령어, 프로세스/소켓/로그/GPU 관측, 복합 장애, 자유 명령 진단, 운영체제와 하드웨어 내부 구조, 기계어 심화 등. 이들을 학기 내 필수 기능으로 한꺼번에 약속하지 않습니다.

원래의 '복합 장애 Chapter 3c + 엔딩부터 구현' 방안은 **새로운 교육 루프보다 우선하지 않습니다**. 기존 Chapter 확장 자체가 최종 목적을 대체하지 않게 합니다.

## 4. 데이터·설계 일관성

- 기존 Python/Tkinter/SQLite 구조를 최대한 재사용합니다. 큰 구조 변경이 필요하면 먼저 사유/대안/이전 비용을 제시합니다.
- 자원 10단위·교육용 회선 값 등을 실제 GPU 성능·네트워크 통계로 오인시키지 않습니다.
- 이상적인 구조는 한 사건 모델 → GUI·다이어그램·터미널이라는 여러 관점의 투영입니다. 이는 **설계 원칙**이며 현재 적용 여부는 코드로 확인합니다.
- 조회·도움말·복습·명령어 설명은 기본적으로 시간·배정·DB를 바꾸지 않습니다.
- 상태 변경 명령은 고객 동의·자원·권한·현재 상태 등을 재검증하고 저장 실패 시 복구합니다.
- 오래된 스토리 슬롯, 완료 기록, 자유 운영 기록을 보존합니다. SQL·JSON 버전을 바꾸면 명시적으로 호환 테스트를 추가합니다.
- 과도한 리팩터링보다 작은 수직 기능을 검증하고 학습 결과를 평가합니다.

## 5. 새 기능 승인 전 체크

- **상태:** 구현/진행 중/제안 중 어느 것인지 확인.
- **학습:** 사용자가 습득할 원리와 초급→심화 연결 방법.
- **사실성:** 실제 명령/네트워크와 교육용 추상화의 차이.
- **사용성:** 처음 보는 사람도 관찰→조작→결과를 연결 가능한지.
- **검증:** 정상·오류·저장·재시도·오래된 슬롯·GUI 동작.
- **범위:** 이번 개발에서 꼭 필요한가, 더 작은 구현으로 검증 가능한가.

**사용자 동의 없이 새로운 단계로 자동 진행하지 않습니다.** 기술 설계의 핵심 선택·범위 변경은 먼저 설명하고 합의한 뒤 구현합니다.
