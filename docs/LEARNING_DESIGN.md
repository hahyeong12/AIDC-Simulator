## 1. 기본 교육 모델: 도움의 점진적 제거

Scratch/Entry처럼 처음에는 의미가 읽히는 조작을 제공합니다. 그 뒤 같은 사건에서 점차 표현을 실제 명령어와 시스템 자료로 바꿉니다. 난이도를 높이는 것은 창을 더 복잡하게 만드는 행위가 아닙니다.

| 레벨 | 표현 | 조작 | 확인해야 할 학습 |
| --- | --- | --- | --- |
| L0 관찰 | 이야기, 캐릭터, 자원 HUD | 클릭·자연어 선택 | 무엇이 문제인지 구별 |
| L1 연결 | 라우터/스위치/서버 구조도와 상태 | 설명이 있는 명령어 객관식 | 명령이 어떤 정보를 보는지 |
| L2 구성 | 블록형 명령어/옵션/대상 조립 | 제한된 문법 조합 | 구문·옵션·인자 의미 |
| L3 진단 | 가상 터미널·출력·로그·패킷 흐름 | 부분 힌트/자율 입력 | 관찰과 원인 추론 |
| L4 실전 | 같은 환경의 복합 장애 | 힌트 최소·자유 입력 | 가설→증거→조치→검증 |
| L5 확장 | 서비스 내부/OS·컴퓨터 구조 | 선택적 심화 실습 | 추상화 아래로 파고들기 |

레벨 상승 시 이전 GUI를 무조건 삭제하지 않습니다. 필요할 때 되돌아보고 개념을 비교할 수 있게 하되, **도전 과제는 정답 버튼을 눌렀다는 이유만으로 통과시키지 않습니다**. 학습자 편의와 평가의 독립성을 구분합니다.

## 2. 학습에서 지켜야 할 네 가지 연결

1. **자연어 ↔ 구조**: "연결이 안 된다"는 보고를 고객, 라우터, 게이트웨이, 서버, 서비스의 구조도에 연결.
2. **구조 ↔ 명령어**: 무엇을 알고 싶은지에 따라 관찰 도구(`ping`, `ip`, `ss`, `journalctl` 등)를 선택.
3. **명령어 ↔ 결과**: 명령 결과의 값, 오류, 불확실성을 해석하고 시각화에서 동일한 상태를 관찰.
4. **결과 ↔ 행동**: 가설을 검증하고 적절한 조치 후 같은 관찰로 정상화 여부를 확인.

실제 통신을 그대로 복제할 수 없으면 게임 속 모형임을 표시합니다. '보이는 패킷'과 실제 패킷 캡처를 혼동하지 않습니다.

## 3. 동일 사건을 관찰하는 세 가지 인터페이스

- **운영 GUI**: 기존 관제실, 고객 요청, GPU·전력 및 기한, 장애 알림과 결과.
- **구조 시각화**: 고객→라우터/게이트웨이→스위치→서버/서비스, 패킷·연결 상태·서버 프로세스·자원 변화 애니메이션.
- **가상 Linux 터미널**: 제한된 명령어, 타당한 옵션과 인자, 현재 시뮬레이션 상태에서 생성한 결과.

세 화면은 서로 다른 임의의 데이터를 보여주는 장난감이 되어서는 안 됩니다. 공통 상태(같은 가상 시간, 같은 서버, 같은 장애 원인)에서 관측 뷰를 만들고, 허용된 조치는 해당 상태를 변경해야 합니다.

가능하면 상태→진단 결과→시각화가 결정적이고 재현 가능해야 합니다. 관찰/명령어 검색/복습은 기본적으로 읽기 동작이고 시간·자원을 바꾸지 않습니다. 상태 변경 명령은 사전 조건·실패·권한·검증·기록을 갖춥니다.

## 4. 사례: 같은 '고객이 서버에 연결하지 못한다'는 문제

### L0

선배가 "네트워크 진단"을 안내하고, 경로/대역폭 정보를 보여줍니다. 플레이어가 우회 또는 압축을 선택합니다. 기존 Chapter 3a와 연결됩니다.

### L1

화면에 고객, 경유 장비, 서버 위치를 그립니다. 플레이어는 "연결 시험", "경로 확인", "서비스 포트 확인" 등 의미가 쓰인 명령어 카드를 고릅니다. **무슨 질문에 답할 도구인지**를 학습합니다.

### L2

블록을 `ping` + `-c 3` + `10.0.0.20`처럼 조합하여 실제 명령 구문으로 바꿉니다. IP가 무엇인지, 횟수 옵션이 무슨 의미인지 안내하고 출력과 연결합니다.

### L3

가상 프롬프트에서 스스로 `ping -c 3 10.0.0.20`, `ip route`, `ss -lnt` 등을 실행합니다. 단일 결과로 모든 원인이 확정되지 않는다는 점을 학습합니다. 예: ICMP 응답이 없다는 사실만으로 회선 단절을 단정하지 않습니다.

### L4

서버 통신은 되지만 서비스가 닫힌 경우라면 `ss`, `systemctl status`, `journalctl` 등 다른 증거를 확인하도록 합니다. DNS 오류/라우팅 오류/서비스 종료는 게임 시나리오의 서로 다른 원인이어야 합니다. 원인별로 적절한 조치가 달라지고, 조치 후 재확인을 요구합니다.

### L5

원한다면 TCP 연결 과정, 패킷·소켓·프로세스 관계, 커널/장치 계층까지 탐색합니다. **기계어·커널 분석은 미래 확장**으로 표기하고 이번 학기 필수 목표로 간주하지 않습니다.

### 네트워크 장애 모델링의 주의

- `ping`은 ICMP 연결 가능성의 한 단서일 뿐, 애플리케이션 전체 정상 작동을 증명하지 않습니다.
- DNS 질의, TCP 연결, HTTP 응답, 링크 상태, 라우팅 상태를 서로 다른 현상으로 다룹니다.
- 패킷/회선의 애니메이션은 교육용 모식도임을 표시합니다. 라우터·스위치의 역할은 현실 네트워크 원리에 맞춰 설명합니다.
- 우회·압축·재시작이 무조건 모든 장애를 해결하는 만능 버튼이 되어서는 안 됩니다.
- 현재 Chapter 3a의 네트워크 구성은 교육용 가상 설정이므로 새 진단 모델과 맵핑하기 전까지 실제 장비 동작인 것처럼 묘사하지 않습니다.

## 5. 명령어 교육 범위 — 우선순위 제안

| 묶음 | 기초 명령 예 | 배우는 질문 | 범위·주의 |
| --- | --- | --- | --- |
| 연결 | `ping`, `ip addr`, `ip route` | 주소와 경로를 어떻게 확인하는가? | 명령별 관찰 범위 명시 |
| 이름·서비스 | `getent hosts`, `ss -lnt`, `curl` | DNS와 포트와 서비스는 무엇이 다른가? | `curl`은 OS 별도 패키지일 수 있음 |
| 서버 운영 | `ps`, `top`, `free`, `df` | 프로세스/메모리/디스크 상태는? | 지표와 실제 원인 혼동 방지 |
| 로그 | `systemctl status`, `journalctl` | 서비스를 누가/왜 중지했는가? | systemd를 쓰는 가상 Linux 가정 명시 |
| GPU/전문 심화 | `nvidia-smi` 등 | GPU 사용과 작업은 어떻게 연결되는가? | NVIDIA 도구 의존, 게임 GPU 수치와 실제 성능 분리 |

이 표는 **학습 커리큘럼 후보**이지 현재 지원 명령 목록이 아닙니다. 초기에 전체 셸을 구현하지 않습니다. 몇 개의 관찰 명령부터 정확하게 지원한 후, 실제 게임 사건과 연결된 안전한 조치 명령을 추가합니다.

## 6. 가상 터미널 설계 원칙

- **실제 호스트 OS에서 명령을 마음대로 실행하지 않습니다.** Windows에서 실행되는 Python/Tkinter 게임 안의 격리된 교육용 명령 해석기를 우선합니다.
- 명령어 토큰/옵션/대상은 허용 목록으로 해석하고, 지원하지 않는 명령은 '지원하지 않음'을 명확히 알려줍니다. 실제 Linux 셸이라고 속이지 않습니다.
- 명령 결과는 미리 정해둔 정답 문자열만 돌려주는 것이 아니라 가능한 범위에서 **현재 서버/네트워크/서비스 상태로 계산**합니다.
- 구조도/애니메이션/터미널 로그/점수는 하나의 상태를 바탕으로 계산합니다. 한 화면에서 DOWN, 다른 화면에서 UP이라고 말하지 않습니다.
- 읽기 명령과 변경 명령을 구별하고, 변경 명령은 권한·전제 조건·시간·부작용·실패를 모델링합니다.
- 파괴적 명령어, 실제 네트워크 설정 변경, 사용자 파일 조작은 실습 범위에 넣지 않습니다. 향후 실제 Linux 실습은 별도 격리된 환경과 명시적 동의 아래 설계합니다.
- 설명 없이 정답 명령을 자동 입력하지 않습니다. 초반의 힌트/객관식/블록은 점진적으로 줄입니다.
- 오류 메시지도 학습 자료입니다. 실제와 다른 메시지를 쓰는 경우 '교육용 출력'을 표시합니다.

## 7. 학습 효과와 평가

단계 통과를 '정답 선택 여부'만으로 판단하지 않습니다.

1. 관찰: 어떤 정보와 증거를 얻었는가?
2. 설명: 그 정보가 무엇을 의미하는가?
3. 가설: 어떤 원인들을 고려했는가?
4. 조치: 왜 그 조치를 선택했는가?
5. 검증: 동일/다른 관찰로 정상화됐음을 확인했는가?
6. 회고: 잘못된 가설을 어떻게 수정했는가?

힌트 사용은 죄가 아닙니다. 다만 고급 레벨의 숙련 확인에서는 필요한 정보를 직접 찾아야 합니다. 점수는 자원/고객 기한과 학습 피드백을 분리하거나 명확히 구분해, 학습 점수와 게임 운영 점수가 서로 혼동되지 않도록 합니다.

## 8. 미션 및 UX 설계 체크리스트

- 새 개념을 추가할 때 **실제 의미 → 쉬운 비유 → 화면에서 관찰 → 명령어 → 재확인**을 연결했는가?
- 어느 계층(물리/링크/IP/전송/애플리케이션/OS)이 문제인지 맞게 설명하는가?
- 선배/힌트가 먼저 정답을 누설하지 않는가?
- 누른 버튼·조립한 명령·입력한 명령이 동일 사건에 반영되는가?
- 비GUI 상태 테스트와 GUI 상호작용 테스트, 잘못된 명령/순서 테스트를 갖추었는가?
- 가상 모델과 실제 네트워크/리눅스에서 차이가 나는 부분을 표시했는가?
