# AIDC Simulator

> **v0.9-3b** · 2026-11-10 · Python / Tkinter / SQLite · 추가 패키지 없음

**Python 기반 AI 데이터센터 운영 시뮬레이션**입니다. OSS 텀프로젝트로 개발 중인 개인 프로젝트이며, 가상의 울산 AI 데이터센터를 배경으로 하는 미션 게임입니다.

플레이어는 신입 엔지니어로 입사하여 단계별 미션과 이야기를 따라 데이터센터 운영을 배웁니다. 현재 **v0.9-1d**는 중앙 주요 대화(STORY), 실제 조작 안내(ACTION), 행동 근처의 성공 피드백(FEEDBACK)을 구분합니다. 독립 스토리 슬롯과 Chapter 1 교육을 유지하며, 고객 조건 요약과 배정 카드 전체 선택을 제공합니다. 기존 고객 요청·자원 배정·동시 작업·네트워크 및 서버 장애 대응은 자유 운영 모드에서 계속 플레이할 수 있습니다.

**고객사·네트워크·자원 단위·처리 속도·점수는 교육용 가상 설정입니다. 실제 설비의 성능이나 운영 체계를 재현하지 않으며 외부 서비스에 접속하지 않습니다.**

## 개발 동기

AI 데이터센터와 서버 인프라 분야에 대한 관심에서 시작했습니다. 실제 AI 컴퓨팅 자원 운영과 데이터센터 업무를 참고하여 고객 요청을 접수하고, 자원을 배분하며, 운영 중 발생하는 문제에 대응하는 게임을 만들고자 했습니다.

단순한 과제 완성보다 관심 분야를 탐구하고, 직접 기획한 프로그램을 지속적으로 발전시키는 것을 목표로 합니다.

## 주요 게임 기능

- **스토리 모드:** 교육 담당자의 첫 출근 안내, 실제 관제실 조작으로 진행하는 튜토리얼과 첫 고객 업무
- **모드별 이어하기:** 시작 화면에서 스토리/자유 운영을 선택하며 각 모드의 기록을 독립 저장
- **새 스토리와 저장 슬롯:** 기존 완료 기록을 보존한 채 첫 출근부터 새로 시작하거나 원하는 스토리 슬롯 이어하기
- **AIDC LINK 사내 메신저:** 해외 고객의 AI 작업 요청과 상태별 대화, 새 메시지 알림 및 대화 기록
- **요청 의사결정:** 수락·대기·거절, 고객별 GPU·전력 요구량과 기한 확인
- **고객 조건과 대안 동의:** 지정형·유연형 요청을 구분하고, 허용 범위 밖의 절약형은 AIDC LINK에서 고객 동의를 받은 뒤 배정
- **운영 모드와 동시 작업:** 고성능·절약형 선택, 여러 고객 작업의 GPU·전력 공유
- **서버 배정 계획 선택:** 자동 추천과 최대 2개의 대안을 비교하고 직접 선택한 서버·GPU 슬롯·전력으로 실제 작업 시작. 자동 배정도 유지
- **자원 관제:** GPU 반도체 모듈·전력 배터리, 서버 Inspector와 시작 전 추천 배정안·잔여 자원·예상 완료 시각 미리보기
- **가상 시간과 자동 접수:** 시간 버튼에 따른 작업 진행률 증가 및 새로운 고객 요청 도착
- **장애와 후속 조치:** 네트워크 장애 대응·복구, 실패 후 재처리 또는 처리 불가 보고
- **개별 서버 장애와 이전:** 교육용 서버 장애, 가상 시간 20분 장비 복구, 기존 수행·진행률을 유지하는 작업 이전과 10분 준비
- **기한과 기록:** 고객별 완료 기한·지연 관리, 운영 결과·SQLite 기록 저장 및 종료 후 이어하기

## v0.9-3b Chapter 3b · 서버 장비 장애 — 장비 복구 vs 작업 이전

Chapter 3a(네트워크 장애)를 **성공**으로 마친 스토리의 결과 화면에서 **[Chapter 3b 시작]**을 누르거나, 스토리 메뉴의 **[Chapter 3b 새로 시작 · 연습]**(독립 슬롯)으로 시작합니다. **[Chapter 3b 이어하기]**는 진행 중인 최근 슬롯을, **[Chapter 3b 다시 도전]**은 항상 새 슬롯을 엽니다. 3a의 저장·결과는 소급 변경하지 않고, 독립 연습은 이전 Chapter를 완료했다고 기록하지 않습니다.

- **핵심:** 장애가 났다고 무조건 이전하지 않고, 정상 서버의 실제 여유 자원과 고객 완료 기한을 비교해 직접 선택합니다.
- **미션 A · 이전이 유리한 경우(일본, GPU 3/전력 4, 완료 기한 접수+75분):** 작업량 40%에서 Server A 장애. 이전(준비 10분)은 시작+70분에 끝나 기한을 지키고, 장비 복구(20분)는 +80분에 끝나 5분 늦습니다. 시간은 기존 엔진이 계산한 결과입니다.
- **미션 B · 이전이 불가능한 경우(싱가포르, GPU 7/전력 7):** Server A 장애. 정상 서버(B·C·D)의 GPU는 6개뿐이라 전체 작업 이전이 불가능하고, 장비 복구(20분) 뒤 기존 배정 그대로 재개해 기한 내 완료합니다.
- **[장비 진단]:** 장애 서버·상태, 영향 작업, 점유 자원, 정상 서버 가용량, 작업 이전 가능 여부(불가 이유 포함), 복구·이전 예상 완료와 기한 준수 여부를 표로 보여 줍니다. 진단을 연 뒤에만 [장비 복구 · 20분]과 [작업 이전 계획]을 선택할 수 있고, 진단창은 아무것도 자동 선택하지 않습니다. 이전은 기존 배정 카드 창에서 직접 고릅니다.
- **시간:** 복구/이전을 선택해도 시간은 흐르지 않고 시간 버튼으로 진행합니다. 복구 중·이전 준비 중에도 다른 고객 작업은 계속 진행하며, 이전 시 진행률·운영 모드·기한·고객 동의·총 점유는 유지됩니다. 이전이 불가능하면 원장과 시간은 변하지 않습니다.
- **피드백·결과:** 선택 직후 짧은 결과 카드(실제로 고른 대응만 설명). 결과표는 미션 · 장애 · 선택 대응 · 결과 · 중단 · 점수이며 기한 초과 완료는 MISSION FAILED(실제 사유 표시)입니다. 실패해도 자동으로 다음으로 넘어가지 않고 [Chapter 3b 다시 도전]/[후속 처리로 돌아가기]를 직접 고릅니다.
- **자유 운영:** 수동 서버 장애·복구·이전, 한 서버의 장애가 다른 서버의 작업을 멈추지 않는 동작은 그대로입니다. 교육용 자동 장애는 Chapter 3b 스토리에서만 발생합니다.

- **복귀:** 복구 성공 카드(상태 행 추가)의 [업무로 돌아가기]는 시간을 진행하지 않습니다. [복구 준비 10분 진행]은 선택 기능이며 +10/+30/+60분 중 원하는 방식으로 진행해도 됩니다. 복구 준비는 가상 시간으로만 진행되고, 그동안 다른 고객 작업을 배정·진행해도 GPU·전력 원장은 그대로입니다.
- **스토리:** 복구 준비 중에는 "복구 준비 확인", 정상 실행 후에는 "남은 고객 작업 완료"로 목표가 바뀝니다. 미션 B는 여전히 미션 A 작업이 실제로 끝난 뒤에 열립니다.

## v0.9-3a Chapter 3 · 네트워크 장애 진단과 대응

Chapter 2를 **성공**으로 마친 스토리의 결과 화면에서 **[Chapter 3 시작]**을 누르거나, 스토리 시작 메뉴의 **[Chapter 3 새로 시작 · 연습]**으로 새 독립 슬롯에서 시작합니다. 진행 중인 Chapter 3 기록은 **[Chapter 3 이어하기]**로, 결과 화면·상단 바의 **[Chapter 3 다시 도전]**은 항상 새 슬롯에서 처음부터 시작하며 현재 기록은 보존합니다. 독립 연습은 Chapter 1·2를 완료했다고 기록하지 않고, 실패한 Chapter 2 슬롯은 Chapter 3을 해제하지 않습니다.

- **장애 버튼을 누르는 게임이 아니라 원인을 보고 판단하는 게임:** 작업 중 지정된 지점(작업량 40%)에서 장애가 결정적으로 발생하고, 남은 시간 진행은 그 자리에서 멈춥니다. 관제실의 **[네트워크 진단]**을 열어야 대응 버튼이 활성화됩니다. 선배는 무엇을 확인할지만 안내하고, 진단 전에는 정답 대응을 알려 주지 않습니다.
- **미션 A · 통신 경로 단절(싱가포르):** 주 경로 DOWN, 가용 대역폭 0, 백업 경로 UP(용량 6), GPU·서버 정상. **백업 경로 우회**만 복구합니다. 압축은 필요 대역폭을 줄이지만 끊어진 경로를 되살리지 못해 작업이 재개되지 않습니다.
- **미션 B · 가용 대역폭 부족(미국):** 주 경로 UP, 가용 4 < 필요 6(절약형 5), 백업 경로는 같은 병목 구간을 공유해 용량 증가 없음, GPU·서버 정상. **데이터 압축**만 복구합니다(필요량 −2). 백업 경로 우회로는 병목이 해소되지 않습니다.
- **잘못된 대응도 실제 결과:** 대응은 기록되고 기존 비용(우회 15·압축 10·유지 25)과 점수 규칙에 반영되며, 선배는 정답 대신 관찰된 수치(필요/가용·경로 상태)를 알려 주고 재진단을 유도합니다. 대응 3회 한도, 60분 장애 중단 실패, 실패 후 재처리·최종 보고, 자원 반환은 기존 규칙 그대로입니다.

Chapter 1에서는 추가 고객 자동 접수와 확률적 네트워크 장애를 사용하지 않습니다. 건너뛰어도 이 정책을 유지하며 첫 업무 이후 새 미션을 생성하지 않습니다. GPU 부족·국제망 장애 미션은 아직 제공하지 않습니다. 자유 운영 모드의 기존 사건 규칙은 유지합니다.

스토리 상태는 세션에서 관리하고 기존 SQLite `simulation_state` JSON에 게임 상태와 함께 저장합니다. 각 단계·튜토리얼 완료·첫 업무 완료를 종료 후 이어가며 저장 오류 시 실제 작업과 안내 진행을 함께 복구합니다. `SimulatorApp(root, db=...)` 직접 생성은 기존처럼 자유 운영이고, 스토리 직접 생성은 `mode='story'`를 사용합니다.

**v0.9-1 저장도 보존합니다.** 진행 중이면 기존 단계/실제 수행에 맞춰 연결하고, 이미 튜토리얼을 완료한 기록은 유지합니다. 이미 첫 업무를 정상 완료했다면 즉시 Chapter 완료 결과를 볼 수 있습니다. 작업 재실행·중복 수행 생성·점수 재계산은 하지 않습니다. SQL 구조는 그대로이며 스토리 JSON만 버전 2로 연결합니다.

**v0.9-1a도 그대로 이어갑니다.** 스토리 JSON 버전 2에 선택 필드 `dialogue_seen`만 추가했습니다. 필드가 없으면 지난 교육 단계의 대화를 이미 표시한 것으로 읽고 현재 장면부터 연결합니다. 기존 Chapter 완료·요청·수행·점수·기한·배정 이력을 보존하며, 완료 저장은 새 교육 대신 기존 완료 화면을 엽니다. 새로운 첫 출근 체험은 별도의 임시 DB에서만 검증했습니다.

## 플레이 방법

1. **고객 요청 확인:** 처음 실행하면 09:00에 싱가포르 고객의 요청이 도착합니다. AIDC LINK의 `요청 확인`이나 요청 목록을 눌러 내용을 읽습니다.
2. **자원과 기한 비교:** 오른쪽 패널에서 가용 GPU·전력, 두 모드의 예상 완료 시각과 기한 준수 여부를 비교합니다.
3. **배정 계획 선택·요청 결정:** 고객이 요청하거나 허용한 모드를 선택하고 오른쪽 `배정 계획 비교·선택`에서 계획을 비교·선택한 뒤 `선택한 계획으로 작업 시작`을 누릅니다. 기존 `배정하고 작업 시작`은 자동 추천으로 시작합니다. 지정형의 절약형은 먼저 `대안 제시` → `고객 답변 확인`으로 동의를 받아야 합니다. `수락만 · 배정 대기`는 실행이나 모드 변경 동의를 의미하지 않습니다. 거절에는 사유가 필요합니다.
4. **게임 시간 진행:** `+10분`, `+30분`, `+60분`을 누르면 모든 정상 작업이 함께 진행됩니다. 시작 직후 0%는 정상이며, 요청을 읽는 동안에는 시간이 자동으로 흐르지 않습니다.
5. **새 요청과 동시 운영:** 시간이 흐르면 새 요청이 자동 도착합니다. 기존 작업을 유지하면서 여유 자원에 다른 고객의 작업을 배정할 수 있습니다.
6. **장애와 지연 대응:** 장애가 난 작업을 선택해 백업 경로 우회·데이터 압축 등의 대응을 합니다. 정상인 다른 작업은 계속 진행됩니다. 기한이 지난 작업은 늦게 완료할 수 있지만 감점이 남습니다.
7. **결과 확인:** 완료·수행 실패 시 해당 작업의 자원이 반환됩니다. 실패한 작업은 재처리하거나 최종 보고하고, `수행 기록`·`이벤트 / 로그`·`대화 기록`에서 결과를 확인합니다.
8. **종료 후 이어하기:** 창을 정상 종료하면 상태가 저장됩니다. 다시 실행하면 마지막 저장의 시간·요청·작업·자원 배정을 이어갑니다.

서버 장애를 직접 연습하려면 일본 고성능 작업을 시작한 뒤 점유 서버를 클릭하고 Inspector의 `교육용 서버 장애`를 누르세요. `장비 복구 · 20분` 또는 고객 작업의 `작업 이전 계획`을 선택할 수 있습니다. 확정만으로 시간은 흐르지 않으며 준비가 끝난 다음 시간 구간부터 작업이 진행됩니다. 싱가포르 7/7 작업에서 A가 고장 나면 나머지 정상 용량은 6/6이므로 이전할 수 없어 장비 복구가 필요합니다.

## 실행 방법

Python 3.10 이상과 Tkinter가 필요합니다. 프로젝트 폴더에서 실행합니다.

```powershell
python main.py
```

Windows에서 Python 런처가 설치되어 있다면 `py main.py`도 사용할 수 있습니다. Tkinter 설치 여부는 `python -m tkinter`로 확인합니다. Tk 창이 열리지 않고 모듈 오류가 나면 Python 설치 구성의 Tcl/Tk 지원을 확인해 주세요. Linux 등 일부 환경에서는 운영체제의 별도 Tk 패키지가 필요할 수 있습니다.

Anaconda를 사용하고 `python`이 Windows 실행 별칭을 가리키는 경우에는 다음 명령을 참고하세요. Anaconda가 해당 경로에 설치된 경우에만 사용할 수 있습니다.

```powershell
& "$env:USERPROFILE\anaconda3\python.exe" main.py
```

추가 pip 패키지 설치는 필요하지 않습니다. 자유 운영 기록은 `aidc_game.db`, 기존 스토리는 `aidc_story.db`, 새 스토리는 `aidc_story_slot_NNN.db`를 보관해 주세요. 모드 선택 후 스토리 메뉴에서 새 슬롯 생성이나 이어하기를 명시적으로 선택합니다. 실행에는 GUI를 표시할 수 있는 데스크톱 환경과 프로젝트 폴더의 쓰기 권한이 필요합니다.

- **오른쪽:** 서버 클릭 시 Inspector에서 GPU/전력 총량·사용·가용 및 모든 점유 고객을 확인합니다. `배정 미리보기` 탭에서 선택 작업의 조건·추천 서버 조합·서버별 잔여량을 비교합니다.
- **하단:** 선택 작업 정보, 수락·배정·대기·거절 또는 장애·후속 대응, +10/+30/+60분 버튼

관제실 전체의 세로 스크롤을 제거했습니다. 기본 창은 화면 크기에 맞춘 최대 1280×680, 최소 1000×650입니다. 1366×768 화면의 작업 표시줄·창 테두리를 고려했으며, 큰 화면에서는 창을 늘리거나 최대화할 수 있습니다. 긴 메시지·전체 이벤트·수행 기록은 별도 창으로 엽니다.

## AIDC LINK 업무 메신저

새 알림이나 요청 목록을 클릭하면 현재 요청·작업 상태에 맞는 메시지 창을 엽니다. 신규 요청에는 고객사·국가·작업·필요 자원·접수 및 기한을 표시하며 가용 자원과 두 모드의 예상 완료 시각은 운영실 오른쪽에서 비교합니다.

- `이전` / `다음`으로 대화 단계를 이동합니다.
- `전체 보기`는 모든 단계를 별도 창에서 보여 줍니다.
- `다음`은 타이핑 중 현재 페이지를 즉시 완성하고, 완성된 상태에서 다시 누르면 다음 페이지로 이동합니다. 별도의 `즉시 표시` 버튼은 제거했습니다.
- `건너뛰기`는 현재 대화 시퀀스의 마지막 페이지를 표시합니다. 마지막 페이지의 확인 버튼으로 운영실로 돌아갑니다.
- 수락·실행·장애·복구·기한·완료·실패의 고객 메시지를 사건 종류와 게임 시각으로 저장합니다. 새 상태가 되면 이미 지난 최초 요청을 다시 붙이지 않습니다.
- 새 메시지와 확인한 현재 상태 메시지를 구분하며, 운영실의 `대화 기록`은 과거 대화를 시간순으로 보여 줍니다. 기록 열람은 새 알림을 소비하거나 시간을 진행하지 않습니다.

자연어 AI나 실제 메신저 연동을 사용하지 않으며 준비된 메시지를 표시합니다.

## 요청 접수와 의사결정

자유 운영의 첫 신규 게임은 09:00과 첫 싱가포르 요청으로 시작합니다. 이후 시간 버튼으로 게임 시간을 진행하면 **30분마다 자동 접수**를 검토합니다. 기존 작업 진행·완료·장애와 같은 시간 흐름에서 처리하며, 요청이 도착해도 선택한 작업이나 배정 자원을 바꾸지 않습니다. 최초 세 고객을 처리한 뒤에도 자동 접수는 계속됩니다. 스토리 Chapter 1은 첫 싱가포르 요청만 사용합니다.

- 접수 가능한 고객 중 누적 요청이 적은 고객을 우선하고 같은 조건에서는 시드 기반으로 순서를 섞습니다. 싱가포르→일본→미국 순서로 고정하지 않습니다.
- 한 시점에 1~2건이 함께 도착할 수 있습니다. 자동 접수 시 신규·검토·대기·배정 대기 요청의 합계를 최대 2건으로 제한합니다.
- 같은 고객·미션의 요청은 최소 60분 간격이며, 이미 미처리·운영 중이거나 실패 후 조치가 남은 경우 중복 접수하지 않습니다.
- 한도에 도달했거나 가능한 고객이 없으면 그 접수 시점은 건너뜁니다. 과거에 접수하지 못한 요청을 나중에 한꺼번에 쌓지 않습니다.
- 이전 저장에 이미 상한보다 많은 미처리 요청이 있어도 삭제하지 않습니다. 기존 요청을 처리해 여유가 생기면 자동 접수를 재개합니다.
- 수동 `다음 요청 확인` 버튼은 제거했습니다. AIDC LINK 알림에서 고객사·요청 작업·필요 GPU·현재 가용 GPU를 확인하고 `요청 확인`을 누르면 기존 대화창을 엽니다.
- 알림 아래에 다음 접수 검토 시각과 미처리 요청 수를 표시합니다. 요청 검토나 메시지 열람만으로 시간이 흐르지는 않습니다.

요청 상태와 작업 상태는 별도로 관리합니다.

| 요청 관련 행동 | 실제 작업과 자원 |
| --- | --- |
| 요청 확인 | 검토 중, 자원 미점유 |
| 수락만 · 배정 대기 | 수락 의사를 저장하고 작업 상태 `accepted`, 자원 미점유 |
| 수락·자원 배정 | 선택 모드로 최종 배정 후 정상 실행 시작 |
| 요청 대기 | 자동 실행하지 않고 보관, 자원 미점유 |
| 요청 거절 | 사유 필수. 수행 실패·점수와 별도로 저장, 자원 미점유 |

수락 의사만 표시한 경우 기존 요청 행의 검토/대기 상태와 별도로 운영 스냅샷에 수락 상태를 저장합니다. 실제 수행 ID는 최종 자원 배정 시에만 발급합니다.

운영 모드를 선택하거나 마우스를 올리면 요구 GPU·전력과 배정 후 잔여량 또는 부족량을 확인할 수 있습니다. 실제 배정은 최종 버튼을 눌렀을 때만 이뤄집니다. 부족하면 버튼을 비활성화하며 백엔드에서도 배정을 차단합니다.

자원 관제실은 외부 이미지 없이 Tkinter Canvas로 그립니다. 상단은 작은 반도체 아이콘 10개와 전체 가용량, 서버 내부와 Inspector는 PCB·회로·금색 핀·LED가 있는 GPU 모듈을 표시합니다. 가용 GPU는 청록색 `ON`, 정상 점유 GPU는 고객 색상과 `SG/JP/US`로 구분합니다. 슬롯 위치는 수행이 끝날 때까지 유지되며, 한 서버의 여러 고객도 모듈별로 구분합니다.

전력은 GPU와 다른 배터리 형태이며 `가용 25%`는 **전력 가용률**입니다. 정상 서버의 GPU·전력 가용량 0은 전체 배정 상태이고 장애를 뜻하지 않습니다. FAULT/REPAIRING 서버는 가용량 0으로 표시하며 기존 점유와 사용 불가 잔여량을 따로 합산합니다. 점등은 450ms 타이머 하나로 갱신하고 종료 시 취소합니다. 하드웨어 장애는 빨간 랙과 FAULT/REPAIRING, 네트워크 문제는 `NET`과 작업 경고로 구분합니다. 두 문제는 같은 작업에 함께 존재할 수 있습니다.

배정 검토에서는 두 모드의 필요량·가용량·전체 잔여/부족량·예상 완료 시각을 비교하고, 선택 모드의 추천 서버 조합과 서버별 배정 후 잔여량을 표시합니다. 미리보기는 자원과 수행 ID를 점유하지 않습니다. 실행 중에는 실제 배정, 종료 후에는 반환 상태를 보여 줍니다. 재처리 예상 시간에는 전체 작업과 준비 20분을 포함합니다. Inspector와 배정 미리보기는 탭으로 전환하여 작은 화면의 정보 겹침을 줄였습니다.

### 자동 서버 배정 규칙

| 서버 | GPU | 전력 |
| --- | ---: | ---: |
| Server A | 4 | 4 |
| Server B | 3 | 2 |
| Server C | 2 | 3 |
| Server D | 1 | 1 |

서버마다 GPU와 전력을 함께 제공해야 합니다. 신규 배정의 각 조각은 GPU·전력이 모두 양수이며, GPU 1개당 전력 1단위 같은 고정 비율은 없습니다. 사용 서버 수가 적은 조합부터 A~D 순서와 고정 자원 순서로 가능한 배정량을 탐색합니다. 빈 데이터센터의 싱가포르 고성능 7/7은 **A 4/4 + B 2/2 + C 1/1**로 시작합니다. 여러 서버를 써도 진행 시간·기한·점수는 기존 작업 하나의 규칙을 유지합니다.

전체 자원이 남아도 서버별 조합이 안 되면 시작을 차단합니다. 예를 들어 A를 4/4, B를 2/2 점유한 뒤에는 총 4/4가 남지만 B의 GPU와 C의 전력을 분리해서 가져올 수 없어 미국 절약형 4/3은 시작할 수 없습니다. 다른 작업 완료나 장비 복구를 기다려야 하며 일부 자원만 점유한 상태는 남기지 않습니다. 배정·이전은 제시된 실행 가능 안에서 선택합니다. 임의 수치 입력·랜덤 하드웨어 장애·분산 처리 페널티·서버 증설은 구현하지 않았습니다.

완료·거절한 고객에게 명시적으로 새 요청을 받을 수 있습니다. 실패한 작업은 먼저 재처리하거나 최종 보고해야 합니다. 같은 요청의 중복 시작과 같은 미션의 미처리 요청 중복 생성은 차단합니다.

## 최초 고객 조건과 대안 협의 (v0.7-2)

신규 요청에는 작업·원래 운영 모드·모드별 GPU/전력/네트워크 조건·완료 기한·허용 모드를 별도로 저장하고 요청 메시지에 표시합니다. 원래 모드는 모두 고성능이며, 허용 범위는 작업 성격에 따라 정합니다.

| 신규 고객 / 작업 | 유형 | 별도 협의 없는 선택 | 절약형 선택 |
| --- | --- | --- | --- |
| Merlion AI / 모델 학습 | A · 지정형 | 고성능 GPU 7 / 전력 7 | GPU 4 / 전력 4 · 고객 동의 필요 |
| Sakura Robotics / 긴급 추론 | A · 지정형 | 고성능 GPU 3 / 전력 4 | GPU 2 / 전력 2 · 고객 동의 필요 |
| Northstar AI / 배치 분석 | B · 유연형 | 고성능 GPU 6 / 전력 6, 절약형 GPU 4 / 전력 3 | 최초부터 허용 · 협의 불필요 |

지정 환경의 학습과 긴급 추론은 고성능을 기본 조건으로 삼고, 배치 분석은 자원과 시간의 선택을 운영자에게 맡깁니다. 기존 국가별 자원 규칙을 활용하며, 추가 고객은 미국이면 유연형, 그 외에는 기본 고성능 지정형을 사용합니다. **모드 허용은 기한 준수 보장이 아닙니다.** 미국 절약형은 150분이므로 기존 120분 기한을 넘길 수 있고 기존 지연 감점을 그대로 받습니다.

운영 모드 옆에 `고객 원래 요청`, `고객 허용 모드`, `고객 동의 필요`, `협의 중`, `고객 동의 완료`, `고객 거절 · 실행 불가`를 표시합니다. 필요한 자원이 부족하면 `자원 부족`도 함께 표시합니다. 동의가 필요한 모드도 비교를 위해 선택할 수 있지만 시작 버튼과 세션의 실제 배정은 차단합니다.

작업 시작 전 `대안 제시`를 누르면 기존 AIDC LINK 대화창에서 고성능 요청에 대한 **절약형 운영 대안**을 전달합니다. 원래 조건과 제안 조건, GPU·전력 사용량 차이, 예상 처리 시간 차이, 예상 완료 시각과 기존 완료 기한 준수 여부를 표시합니다. 절약형 자원도 부족하면 제안을 차단하고 대기를 안내합니다.

대화 마지막의 `고객 답변 확인`을 누르면 고객이 답변 시점의 정상 처리 예상 시간을 기준으로 판단합니다. **원래 완료 기한 이내이면 수락하고, 초과하거나 이전 요청에 기한 정보가 없으면 거절**합니다. 장애·복구나 추가 대기로 발생할 지연까지 보장하지는 않습니다.

- 제안과 고객 동의만으로는 자원이나 수행 ID를 배정하지 않습니다. 동의 후 `배정하고 작업 시작`을 눌러야 실행하며, 이때 GPU·전력과 동의한 모드/자원 조건의 일치를 다시 확인합니다. 버튼을 거치지 않는 세션 직접 호출도 검증합니다.
- 협의 중에는 시작을 차단합니다. 수락 시 절약형을 선택하며, 거절 시 기존 고성능 조건을 유지하고 절약형 시작을 차단합니다. 원래 고성능 조건으로의 시작은 가능합니다.
- 기존 요청서 본문과 완료 기한은 변경하지 않습니다. 제안별 원본·대안 조건과 수락/거절 사유·시각을 별도 이력으로 저장하고 `대화 기록`에서 확인합니다.
- `대안 · 고객 답변`으로 창을 다시 열거나 저장 후 이어해도 제안과 동의를 중복 생성하지 않습니다. 답변 대기 중 시간을 진행하면 답변 시점의 기한으로 다시 판단합니다.
- 새 요청의 협의는 요청당 한 번입니다. 거절 후 재협의는 제공하지 않으며 원래 조건 실행·대기·요청 거절을 선택합니다. 유연형에는 불필요한 대안 제시 버튼을 표시하지 않습니다.
- 최초 조건이 없는 이전 저장의 직접 선택은 유지합니다. 이미 협의한 이전 요청의 답변 대기·동의·거절 상태도 그대로 적용합니다. 자세한 정책은 아래 저장 호환성 설명을 참고해 주세요.

고객 조건을 줄이는 GPU 분할 협상, 다른 데이터센터로의 이전, 복잡한 협상은 포함하지 않습니다. v0.8-2의 다중 서버 점유는 원래 요구량 전체를 유지합니다.

기본 작업량은 학습 120, 추론 60, 분석 100입니다. 고성능은 가상 1분당 작업량 1, 절약형은 0.7을 처리하며 10분 단위로 완료를 확인합니다. 표는 장애와 복구·재처리 준비가 없는 값입니다. 실제 GPU 벤치마크를 뜻하지 않습니다. 사용자 추가 고객은 기본 학습 규칙을 사용합니다.

## 고객 기한과 운영 전략

**이번 개선 후 새로 접수한 요청**에는 접수부터의 상대 기한을 부여합니다. 이전에 저장된 요청은 기한 평가에서 제외하며 과거 점수를 재계산하지 않습니다.

| 고객 | 우선순위 | 배정 권장 기한 | 완료 기한 | 미배정 최종 종료 |
| --- | --- | ---: | ---: | ---: |
| 싱가포르 | 일반 · 모델 학습 | +60분 | +210분 | +330분 |
| 일본 | 긴급 · 로봇 추론 | +20분 | +70분 | +190분 |
| 미국 | 우선 · 데이터 분석 | +40분 | +120분 | +240분 |

일본 요청은 고성능 60분이면 완료 기한을 지킵니다. 절약형 90분은 즉시 시작해도 기한을 넘기므로 신규 요청의 대안은 거절됩니다. 싱가포르는 절약형 180분도 기한 안에 끝날 수 있어 **고객 동의를 받은 뒤** 자원을 아껴 일본 고성능과 동시 운영할 수 있습니다. 두 작업 모두 고성능이면 전력 11단위가 필요해 동시 배정할 수 없습니다. 처리 속도와 기한 수치는 유지했습니다.

배정 권장 시각에도 미배정이면 일정 문의, 완료 30분 전에는 임박 안내, 완료 기한 다음 10분 구간에는 초과 알림이 발생합니다. 각각 요청당 한 번이며 읽음·재실행으로 반복 생성하지 않습니다. 미배정 최종 종료 시각에는 요청을 철회해 **미처리 평가 0점**을 기록하고 자원을 쓰지 않습니다. 이는 실제 실행 실패와 구분하여 수행 기록 창에도 별도 표시합니다. 이미 실행한 작업은 완료 기한이 지나도 계속 처리할 수 있습니다.

새 요청의 최종 수행 점수는 기존 점수에서 다음 기한 감점을 차감하며 최저 0점입니다.

- 배정 권장 기한을 넘겨 시작: 초과 10분당 2점, 최대 15점
- 완료 기한을 넘겨 종료: 초과 10분당 5점, 최대 50점

분 단위 나머지는 올림합니다. 지연 안내는 기한이나 감점을 없애지 않습니다. 재처리도 원래 요청의 기한을 유지하며, 이미 확정된 실패 수행 점수는 수정하지 않습니다. 대기 시간은 배정 시 확정하고 완료·거절·미처리 종료 뒤에는 증가시키지 않습니다.

요청함에는 상태·대기 분·기한을 간략히 표시하고, 상세에는 접수·배정 권장·완료 기한·남은 시간을 표시합니다. 마감 30분 이내는 노랑, 초과는 빨강입니다. 오른쪽 패널은 두 모드의 처리 분·예상 완료 날짜/시각과 선택 모드의 기한 준수 가능성을 보여 줍니다. 미래 장애는 예측하지 않는 추정치입니다.

`+10분`, `+30분`, `+60분`은 모든 작업을 10분씩 함께 진행시킵니다. 실제 시계나 멀티스레딩으로 진행하지 않습니다. 완료 전까지 자원을 점유하고 완료·최종 실패한 작업의 자원만 반환합니다. 정상 종료 후에도 시간과 작업을 이어갑니다.

작업 시작 직후의 0%는 정상입니다. 예를 들어 일본 고성능 작업은 GPU 3·전력 4를 배정하고 +10분 후 약 16.7%로 진행됩니다. 최초 조건이 없던 이전 요청의 일본 절약형은 GPU 2·전력 2, +10분 후 약 11.7%라는 기존 동작을 유지합니다. `수락만`은 자원을 배정하지 않으므로 `배정하고 작업 시작`까지 선택해야 진행합니다. 장애·복구 준비 중인 작업을 제외한 모든 정상 작업이 함께 처리됩니다.

## 운영 중 장애와 복구

작업은 가용 네트워크 8의 정상 실행 상태로 시작합니다. 일반 플레이에서는 수행별 45% 확률로 작업 진행 약 35~65% 지점에 네트워크 장애가 예정됩니다. 장애 없이 끝나는 작업도 있습니다. 발생 시 가용량이 2가 되고 해당 작업만 진행을 멈춥니다. 정상인 다른 작업은 계속 처리됩니다.

| 대응 | 효과 | 대응 점수 비용 |
| --- | --- | ---: |
| 백업 경로 우회 | 가용 네트워크 +4, 최대 8 | 15 |
| 데이터 압축 | 필요 네트워크 −2, 최소 1 | 10 |
| 기존 설정 유지 | 네트워크 변화 없음 | 25 |

필요량이 가용량 이하면 복구에 성공합니다. **즉시 완료하지 않고 10분 복구 준비 후 실행을 재개**합니다. 부족하면 일시 중단하고 다른 대응을 추가로 선택할 수 있습니다. 실패한 대응의 변경분과 비용도 누적됩니다.

대응 3회가 모두 실패하거나 장애·중단 누적 시간이 60분에 도달하면 이번 수행은 실패하고 자원을 반환합니다. 대응 횟수와 중단 시간은 화면에 표시합니다. 큰 시간 진행 버튼을 누르면 그만큼 중단 시간도 흐릅니다.

## 실패 이후 고객 대응

실패 기록을 지우거나 성공으로 바꾸지 않고 다음 중 하나를 선택합니다.

- **선택 모드로 재처리:** 최초 허용 모드 또는 사전에 동의한 대안으로 자원을 다시 배정합니다. 실행 뒤 새 협의를 시작하는 기능은 없으며, 무동의 모드 변경은 재처리에서도 차단합니다. 새 수행 ID를 발급하고 이전 실패 수행과 연결합니다. 진행률은 0부터 시작하며 준비 20분이 필요합니다. 요청당 최대 2회이고 재처리 횟수당 최종 점수 10점을 추가 차감합니다.
- **고객 지연 안내:** 예상 완료가 고객 기한을 넘거나 실제 기한을 초과한 경우, 장애·복구 문제로 일정 안내가 필요한 경우에만 버튼을 표시합니다. 기한·예상 완료 시각·지연 예상 분 또는 장애/복구 사유를 함께 표시합니다. 정상적인 기한 내 작업과 종료된 작업에는 표시하지 않습니다.
- **안내 중복 방지:** 같은 장애나 같은 예상 완료 일정은 다시 전송할 수 없습니다. 새로운 장애·복구 계획·예상 완료 시각 변경 또는 실제 기한 초과가 생기면 다시 안내할 수 있습니다. 시간 진행만으로 같은 안내를 반복하지 않으며 저장 후에도 유지합니다. 안내 1회당 기존 운영 비용 5점을 적용하고 기한·지연 감점은 유지합니다. 실패 뒤에는 재처리 또는 최종 보고를 선택합니다.
- **처리 불가 보고:** 이유와 피해 사실을 고객에게 최종 안내하고 후속 대응을 마칩니다. 운영 중 선택한 경우 해당 수행을 실패로 기록합니다. 이미 실패한 결과는 덮어쓰지 않습니다.

성공 점수는 `80 + 모드 보너스 − 누적 대응·안내 비용 − 10×재처리 횟수 − 중단 손실 + 10`입니다. 실패는 마지막 +10 대신 −65를 적용하며 전체를 0~100으로 제한합니다. 보너스는 고성능 15, 절약형 5이고 중단 손실은 `min(20, 중단 분//10)`입니다. 과거 실패 기록과 재처리 시간·점수 비용으로 고객 피해를 반영하며 복잡한 만족도 시스템은 없습니다.

## 저장·이어하기·기존 DB

수락·배정·대응·시간 진행·고객 안내마다 관련 요청·수행·이벤트·운영 스냅샷을 한 트랜잭션으로 저장합니다. 시간 진행 중 추가 도착과 여러 작업의 완료도 함께 저장합니다. 저장 실패 시 시간·난수 순서·작업 진행·자원·이벤트·새 요청을 함께 되돌립니다.

정상 종료는 현재 상태를 저장한 뒤 창을 닫습니다. **프로그램 종료만으로 작업을 실패 처리하지 않습니다.** 저장 실패 시 창을 유지합니다. 비정상 종료 후에는 마지막으로 저장에 성공한 시점부터 이어집니다.

기존 `clients`, `missions`, `customer_requests`, `playthroughs`, `event_logs`의 구조와 데이터를 유지하고 다음 테이블을 추가합니다.

| 새 테이블 | 용도 |
| --- | --- |
| `simulation_state` | 가상 시각, 난수 시드·장애 추첨, 다음 자동 접수 시각·접수 순서·고객별 최근 접수 시각 |
| `request_runtime` | 요청별 작업 진행·배정·복구·후속 대응 스냅샷 |
| `request_events` | 게임 시각별 요청·장애·고객 메시지·결과 이벤트 |
| `retry_links` | 재처리 수행과 이전 실패 수행 연결 |

기존 v0.5의 운영 중 요청은 이미 발생해 있던 네트워크 장애와 자원을 유지한 상태로 불러옵니다. 이전 완료 기록은 점수를 재계산하거나 새 재처리 대상으로 바꾸지 않습니다. 요청 연결 없는 이전 수행도 기록 창에서 조회할 수 있습니다. 실제 DB의 임시 복사본에서 확장·재실행 3회를 검증했으며 원본 파일은 수정하지 않았습니다. 게임을 처음 실행할 때 새 테이블이 자동으로 추가됩니다.

자동 접수 개선에는 추가 테이블이나 기존 데이터 초기화가 필요하지 않습니다. 기존 운영 JSON에 접수 일정을 함께 저장합니다. 일정이 없는 이전 저장은 저장된 시간과 작업을 유지하고 현재 시각 30분 후부터 새 일정을 시작합니다. 접수 슬롯별 고유 식별자와 저장된 일정을 사용해 이어하기·저장 실패 재시도에서 중복 또는 누락을 막습니다.

기한·메시지 개선도 SQL 테이블 변경 없이 `request_runtime.payload`를 버전 2로 확장합니다. `terms`에 기한·알림 발생 여부·처리 결과·감점을, `message_read_id`에 대화 확인 지점을 저장합니다. 필드가 없는 이전 저장은 기본값으로 불러오며 `terms`가 비어 있으면 해당 요청의 모든 재처리에 기한 감점을 소급 적용하지 않습니다. 저장 실패 시 중첩된 기한 정보와 대화 확인 지점도 복구합니다.

v0.7-1은 같은 JSON 버전 2에 선택 필드 `proposals`를 추가합니다. 필드가 없는 이전 저장은 빈 제안 이력으로 읽고 다음 저장 시 확장하므로 SQL 테이블·CHECK·기존 요청서·과거 점수를 변경하지 않습니다. 제안과 답변도 트랜잭션에 포함하여 저장 실패 시 이력과 고객 동의 여부를 함께 되돌립니다. 실제 DB의 읽기 전용 임시 복사본에서 3회 재실행·저장 후 기존 32개 수행·151개 로그·17개 요청 등의 보존과 무결성을 확인했으며 원본 DB 해시는 유지되었습니다.

UI/UX 개선의 `delay_notice_key`도 JSON 버전 2의 선택 필드입니다. 마지막 안내의 상황과 일정을 저장하며, 필드가 없는 이전 저장은 기존 `delay_notified`가 참이면 현재 상황을 안내한 것으로 연결합니다. 기존 SQL 테이블과 기록은 유지하고 저장 실패 시 안내 판정·비용·메시지도 되돌립니다.

v0.7-2는 JSON 버전 2의 선택 필드 `conditions`에 최초 고객 조건을 저장합니다. `task`, `requested_mode`, `allowed_modes`, `plans`의 모드별 자원 스냅샷, `due`, `type`을 새 접수 때 한 번 만들고 이후 협의·실행·완료 시 바꾸지 않습니다. 제안과 고객 답변은 기존 `proposals`, 실제 실행은 기존 수행 기록에 따로 남습니다.

| 이전 저장의 상태 | 불러오기와 실행 정책 |
| --- | --- |
| `conditions` 또는 runtime 전체가 없음 | `conditions={}`로 유지. 고객의 과거 의사를 추정하거나 요청서를 다시 쓰지 않으며, 협의 이력이 없으면 기존 두 모드 선택을 유지 |
| `conditions` 없음 + 기존 `proposals` 있음 | 협의 중 실행 차단, 거절된 대안 차단, 동의한 모드/자원 조건과 실제 실행 조건 검사 유지 |
| `terms` 없음 | 기존처럼 해당 요청의 기한 감점 제외. 새 기한을 소급 부여하지 않음 |
| 이미 완료된 수행 | 점수·결과·로그 재계산 없음. 원래 모드/자원으로 표시 |
| 이전 저장 이후 새로 접수됨 | 그 요청부터 명시적인 지정형/유연형 조건 적용 |

SQL 테이블·CHECK 변경이나 데이터 초기화는 없습니다. 저장 실패 시 최초 조건·제안/동의·자원·수행·이벤트·접수 일정을 함께 복구합니다. 실제 DB를 읽기 전용으로 복사해 3회 이어하기·저장 후 기존 53개 수행·322개 로그·39개 요청·354개 요청 이벤트와 SQL 구조·무결성 및 원본 SHA-256 불변을 확인했습니다.

v0.8-2는 같은 JSON 버전 2에 선택 필드 `server_allocations`를 추가합니다. 수행 ID별 서버 조각·고정 GPU 슬롯·전력과 완료된 시도까지의 배정 이력을 저장하고, 현재 운영 수행만 점유 원장으로 복원합니다. 새 SQL 테이블이나 CHECK 변경은 없습니다.

v0.8-3의 직접 선택 배정도 같은 저장 구조를 사용하므로 새 필드나 DB 변경이 없습니다. GUI의 실행 전 선택은 저장하지 않으며 실제 시작에 성공한 서버·GPU 슬롯·전력만 확정 원장으로 저장합니다.

v0.8-4는 `simulation_state` JSON에 `server_health`, runtime JSON 버전 2에 `hardware_downtime`·`migration_left`·`migration_downtime`를 선택 필드로 추가합니다. 없는 이전 저장은 모든 서버 정상·0분으로 읽습니다. 동일 수행의 이전 전후 Allocation을 이력으로 남기며 **현재 원장은 그 수행의 마지막 배정**으로 복원합니다. 복구 잔여 시간·이전 준비·네트워크 상태와 고객 조건도 함께 이어갑니다. SQL 테이블·CHECK는 유지합니다.

v0.9-1은 별도 스토리 DB의 `simulation_state` JSON에 `mode='story'`와 `story`를 저장합니다. 자유 운영 저장에는 스토리 필드를 추가하지 않으며 모드 정보가 없는 기존 저장은 자유 운영으로 읽습니다. 모드가 다른 저장을 잘못 전달하면 오류로 알립니다. SQL 테이블·CHECK와 runtime JSON 버전 2는 그대로 유지합니다.

서버 기록이 없는 이전 진행 작업은 기존 전체 GPU·전력을 유지한 채 여러 작업을 함께 재구성합니다. 복원 위치는 과거 사실이 아니라 현재 구성에 맞춘 위치이므로 `복원`으로 표시합니다. 서버별 결합이 불가능한 과거 조합은 `호환` 원장으로 기존 총점유를 보존하며, 이 경우에만 GPU 또는 전력만 있는 조각을 허용합니다. 새로운 작업에는 이 예외를 적용하지 않습니다. 기존 완료 기록에는 위치를 소급 부여하지 않고 고객 조건·동의·기한·점수·로그를 바꾸지 않습니다. 저장된 서버 원장에 중복 슬롯이나 용량 오류가 있으면 임의로 고치지 않고 로딩 오류로 알립니다.

## 제한 사항과 데이터 관리

이번 서버 관제실에서 검증한 창 크기는 1000×650, 1280×680, 1366×768입니다. 고배율 DPI·다중 모니터·장시간 사용감은 직접 확인이 필요합니다. 같은 DB를 여러 앱에서 동시에 운영하는 방식은 지원 범위에 포함하지 않습니다. 하드웨어 장애는 교육용 수동 주입이며 랜덤/일괄 장애·서버 증설·구매·성능 차이·실제 통신 비용은 없습니다. 운영일별 교대, 실제 자연어 협상이나 외부 서비스 연동도 구현하지 않았습니다.

실제 게임 데이터 `aidc_game.db`와 Python 캐시·개인 IDE 설정은 Git에서 제외합니다. DB는 삭제하거나 초기화하지 않고 별도로 보관해 주세요. 저장 실패 시에는 상태를 되돌리고 정상 종료도 보류하므로 오류 원인을 확인한 뒤 다시 저장할 수 있습니다.
